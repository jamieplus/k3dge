# Re-verify Protocol — Default (12 列验收)

> **事实源**：复审层。审计层见 `audit_default.md`。k3dit 缺失时本文件为 `peers.k3dit.actions.verify` 的 manual 兜底，与 `k3dit check-report` 同义（纯人工核验）。

## 交付前验收（12 列）

报告 `docs/reviews/YYYY-MM-DD-<scope>.md` 表头必须 12 列：

`ID | 日期 | 严重度 | 优先级 | 类型 | 问题描述 | 位置 | 状态 | 处置 | 验证 | 复审 | 验收`

逐项核对：
- **12 列齐备**：表头列数 == 12，表体每行列数 == 12。
- **日期**：`日期` 为 `YYYY-MM-DD`，不得为空（发现/初审日期）。
- **状态枚举**：每行 `状态 ∈ {已修, 待修, 有意留}`，不得为空。
- **处置枚举**：每行 `处置 ∈ {已修, 转 docs/tasks/, 有意留}`；`有意留` 须写否决理由 + 失效条件。
- **悬空闭环**：凡 `待修` 必已转 `docs/tasks/`（或本仓对应任务系统），不得只留在报告里。
- **三态闭环**：`待修 == 0` 方可进入 `seal`；`有意留` 须有理由且未超失效条件。
- **复审枚举**：`复审 ∈ {待复审, 通过, 驳回}`；初审产出时为 `待复审`，审计者验收后落 `通过`/`驳回`。
- **验收闭环**：`复审 ∈ {通过, 驳回}` 时 `验收` 必填，格式 `验收人 YYYY-MM-DD [#reason]`（如 `k3dit 2026-08-27` 或 `manual 2026-08-27 #cli 不可用`），记录谁、何时收口。

## 到达

本文件由 `pipeline.toml` 的 `peers.k3dit.actions.verify.manual` 指向；`k3dge check` 不解析本文件内容，仅审计角色在 `pipelines.on_pre_seal` 阶段按此手验，与 `k3dit check-report` 互为同级降级终点。

## Constraints

L2 入场券须逐条确认（agent 进车间前绑定到任务）：

- 表头 12 列齐备，表体每行列数 == 12
- `日期` 为 `YYYY-MM-DD` 且非空
- `状态 ∈ {已修, 待修, 有意留}`；`处置 ∈ {已修, 转 docs/tasks/, 有意留}`
- `待修` 必已转 `docs/tasks/`，且 `待修 == 0` 方可 `seal`
- `复审 ∈ {待复审, 通过, 驳回}`；`复审` 为 `通过`/`驳回` 时 `验收` 必填 `验收人 YYYY-MM-DD [#reason]`
