# ADR 0010: 先读已敲定设计，再和用户的粗意图对齐

- **Status**: Accepted
- **Date**: 2026-08-24
- **Deciders**: Core Maintainer

## 1. 上下文 (Context)
k3dge 的架构是用户与先前 Agent **一步一步敲定**的（ADR 0001 起）。用户给的是粗意图，说不了、也不该每次把表头说到格子。后到的 Agent 若先发明细则再让用户「确认」，等于逼用户重新设计一遍。

## 2. 决策 (Decision)
1. **先读后说**：动手或加规则前，先读 `docs/adr/`（尤其 0001–0004）和 `docs/architecture/overview.md` §5。那是事实源，不是聊天纪要。
2. **粗意图映射到已有决策**：用户一句话应对到已有 ADR/AGENTS 条款。对得上就执行；对不上就问一句，**不要**先写一套新规程再让用户改。
3. **不替用户细化设计**：门禁粒度、域怎么切、文档谁是判据，已经定过。新 Agent 只补执行缺口（漏触发、漏 sync），不升级成另一套方法论。
4. **k3dge 原意（0001）**：Soft Prompting 不够，所以用目录契约 + 哈希 + git 硬闸，让 Agent 在完成**用户说的任务**时保持代码与 spec 一致。用户负责说做什么；Agent 负责不漂。

## 3. 后果 (Consequences)
- 违反本 ADR 的典型样子：用户说「文档该自动维护」，Agent 立刻发明一张 12 行触发表让用户逐条认。正确做法：对到 §2 契约 / §8 ADR / §11 milestone，缺的只问「是不是就是这些已经写过的时机」。
- 用户在场时仍以用户当轮口令为准；不在场时以 ADR 为准，不靠聊天记忆。
