# Memo: 三 Harness 职责划分（k3dge / k3dit / k3lity）

- **类型**：弱相关
- **念头**：明确三个 harness 在「审什么 / 不审什么 / 硬度 / 时机」上的切分，避免把文档内容审计、思想打分、硬闸混为一谈。
- **触发场景**：在梳理文档审计与硬闸边界时，用户纠正了「ADR 冲突/覆盖应进硬闸」的误判，给出了如下职责矩阵。
- **Date**: 2026-08-31

## 职责矩阵

| Harness | 审 | 不审 | 硬度 | 时机 |
|---|---|---|---|---|
| **k3dge** | 形式：哈希、章节、结构枚举 | 写得好不好、定得对不对 | 硬 | 提交时 |
| **k3dit** | 文档文本质量；ADR 集合自洽（冲突/覆盖）；代码是否遵守已商定 ADR | 商定该不该存在、换一种是否更好 | 结构硬；文本质量可勤可硬；冲突偏 CI | 文档变动时 |
| **k3lity** | 商定/实现好不好：复杂度、重复、类型、设计是否过重、ADR 是否值得、有无更简单的做法 | 契约是否漂、文档像不像该类文档 | 必须软 | 里程碑时（对变更文档） |

## 关键澄清（用户原话要点）

- 文档审查**不是给文档表达的思想打分**，而是弥补硬闸查不到的**文本质量**部分。
- ADR 的**冲突和 overlap** 是文档内容检测，需在**文档变动时**做（k3dit，偏 CI）。
- 给文档表达的思想打分（商定/实现好不好）归 **k3lity**，在**里程碑时**对变更文档做，必须软。
- **5-pass 审计只能针对代码，不能针对文档**（文档是另一套规则）。

## 推论（实现落地用）

- ADR 冲突/覆盖检查 = k3dge 提供的**非阻断 sidecar 工具**（`k3dge adr audit <改动文件>` + MCP 同构），由 k3dit 在文档变更时调用；不是 `evaluate()` 里的硬闸，不判「定得对不对」。
- k3dge 形式闸只管确定性结构（哈希/章节/枚举），与文档文本质量、思想打分彻底解耦。
- 文本质量（写得好不好）→ k3dit 的 LLM 部分；思想是否值得 → k3lity 里程碑软审。
