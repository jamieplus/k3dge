## 待拼的碎片（本 memo 主体，均未定型）

### S1 「分形」比喻可能不准

- 直觉怀疑：分形限制过死，且无判断其适用性的能力
- 替代候选：**有限状态机** / **有限分支树**
- 我的分析（待确认）：这里其实混了两个不同结构
  - **生命周期**（状态机）：artifact 处于何态、合法转移为何 → `state_machine.py`（task FSM）、`nextstep.STATE_OPTIONS`（state→options 表）
  - **执行**（决策树 / DAG）：给定态，跑哪些步骤、何序、如何分支 → `gates [checks.*]`、`pipelines.*`
  - 「自相似」的部分不是分形（无无限递归），而是**两者都用同一形状的声明表 + 统一派发**
  - ⇒ 准确表述可能是「两张有限表（态转移表 / 步骤表）+ 一套统一派发」，而非分形

### S2 编排应把投影的连接「从书信降维成决策链」

- 现状类比：连接两个投影时，靠一段**叙事**交接（"审计发现 3 个待修，建议修复，修复后重审"）——像写信
- 目标：降为**决策结构**
  ```
  叙事:  "审计发现 3 个待修…"
  决策:  {state: audit_open, pending: 3, ask: …, if_y: …, if_n: …}
  ```
- 已有部分实现：`nextstep.STATE_OPTIONS` 正是这个形状（state → ask/if_y/if_n/pointers）
- 待确认：是否所有投影连接都能这样降维，以及降维后人类可读性是否受损

### S3 「固定形状，不固定内容」= 戴着镣铐跳舞

- 固定的是 **schema**（容器形状、通道语义、纯度约束）——
  ```
  Step = { name, role: check|act|fix, purity: read-only|mutating, needs, produces }
  ```
- 自由的是 **content**（步骤实现、判据内容）
- 「镣铐」的机制＝新行为只能以已知形状加入（防杂乱生长）
- 待确认：「镣铐」该多紧——太紧则表达力不足，太松则退回杂乱

### S4 编排需不需要主观判断参与，还是机械化就足够

- 现有立场（ADR-0006 §2.3.6 双主体铁律）：**进程永不判断**；判断落具名席位
- 我的分析（待确认）：编排器应是「**消费判定、但不生产判定**」的决策树执行器
  - 判定来源两类：机械检查（确定）/ 具名席位（判断）
  - 编排本身机械；判断点只是分支点，不改变编排的机械性
- 待确认：这条边界是否够用，还是存在「必须由编排器自己判断」的场景

### S5 JEV 式判据（概率分布 + 结构化判据替代完整交互接口）

- 输入：某新模型提出，决策节点无需完整人机交互，只需提供**概率分布**与**结构化判据**
- 我的初步分析（待确认，含保留意见）：
  - **结构化判据 = 高价值**：把「判断」降解为「判据」，消歧义
    ```
    模糊: "审计闭环了吗？"                       （不同 agent 解释不同）
    判据: 待修=0 ∧ 报告存在 ∧ 基线匹配            （无解释余地）
    ```
  - **概率分布 = 存疑**：LLM 自报的 0.7 通常不校准，不是真 70%
  - 建议边界：**概率只作咨询输入，不参与闸判定**（否则破坏 k3dge 的确定性根基）
- 待确认：结构化判据能覆盖多少原本需要判断的点；残余的不可降解判断如何最小化并署名

## S6 【重要修正】三层拓扑——agent 的工作流不可被 k3dge 编排

讨论中被指出的关键区别：**k3dge 是给 agent 用来 vibe coding 的工具，不是像 audit 那样的席位。** agent 通过 CLI 贯穿始终；把 agent 放进步骤的笼子里是**破坏性**的。

### 三层各有不同关系，不可混用同一种编排

| 对象 | 关系 | k3dge 的角色 | 机制 | 现状 |
|---|---|---|---|---|
| k3dit（席位） | **原子调用** | 客户端 | `pipeline.toml` stages | ✅ 已有（ADR-0006 §2.3.8） |
| k3dge 自身内部步 | **编排** | 拥有者/执行者 | `gates [checks.*]` preconditions/actions | ✅ 已有 |
| **agent 的工作流** | **只提供事实与合法选项** | **工具/仪表** | `nextstep` `[NEXT]` | ✅ 已有，**且不得被编排** |

### 约束原文（本仓早已写下）

```
src/k3dge/engine/nextstep.py:20-22
Constraints (design review):
  - success -> state; failure -> action. Never decide for the human.
  - only legal options, no "now execute seal".
```

### 由此修正的方向

- 「大编排器」提案**越界**：它把「k3dge 内部机械步可编排」错误推广到「agent 的工作流可编排」
  - 前者：归属与判断均在 k3dge 内部 ⇒ 可编排
  - 后者：判断是 agent 的本质 ⇒ 编排 = 剥夺判断 = 把工具变成监工（违 ADR-0009 本意）
- 判别标准：**可编排 ⇔ 该过程的「归属」与「判断」在同一主体内，且该主体就是编排者**
- `[NEXT]` 的语义是**广告牌**（列合法选项），不是**调度指令**；应机检它有没有越界成命令

### 可机检形态（已发现现成违规）

不变量：`ask` ↔ (`if_y` ∧ `if_n`)；播报态（仅 note）不得有分支。

实测：`ratchet_open` 有 `if_y` 无 `ask` ⇒ 渲染出**悬空分支**：

```
[NEXT] state=ratchet_open milestone=M10
  if y: k3dge audit status <job> 查对端；…     ← 有 "if y" 但没有问题
  note: 有在办棘轮工单（ADR-0025）…
```

⇒ 一个 ~10 行的校验器即可覆盖。

## S7 【重要补全】双主体铁律的消费侧延伸 + 投影语法

### 一条铁律，管两头

ADR-0006 §2.3.6 的「双主体铁律」（进程 / 席位）**只管「产」**：谁有权产出判断。

本讨论补上「**消**」：

| 侧 | 规则 | 状态 |
|---|---|---|
| **产**（已有） | 进程永不判断；判断须署名席位 | ✅ ADR-0006 §2.3.6 |
| **消**（本次补） | 投影给**判断主体** → 背景 + 建议选项，由它决定<br>投影给**进程** → 按机械步骤执行 | ⬜ 待落 ADR |

### 判断主体内还有两通道（由「有无应答通道」分）

| 通道 | 有应答吗 | 例 | 语法 |
|---|---|---|---|
| 交互 | ✅ 写 prompt 后读 stdin | `prompt.ask` | **疑问句**（y/N、倒计时都是真的） |
| 展示 | ❌ 纯打印，命令即退出 | `[NEXT]` / `STATE_OPTIONS` | **陈述句**（问了无人回答） |

> 一句话：**疑问句是「交互形态」的语法；无交互时借用它，就是语法错误。**

### 证据（E45–E47）

```
E45  nextstep.py 无任何读输入 ⇒ [NEXT] 是纯展示
E46  prompt.ask 写 prompt 后读 stdin ⇒ 有应答通道

但 [NEXT] 里写着：
  audit_suggested: "要审吗？(y/N，无倒计时)"          ← 没人会按 y/N
  seal_ready:      "审计已闭环（待修=0），封板？(y/N，无倒计时)"
  audit_open:      "agent 修？(倒计时默认修)"          ← 无倒计时在跑
```

`(y/N，无倒计时)` 是从 `prompt.ask` 词汇里**误植**的——y/N 与倒计时真实存在于 `run_seal_flow` 的 `prompt.ask(...)`，而 `[NEXT]` 那行只是打印。**这是虚假承诺。**

### 工程收益：陈述可校验，疑问不可

```
"审计已闭环（待修=0）"   → 可验证断言（可拿来比对真状态）
"要审吗？"              → 无真值，不可验
```

⇒ 改陈述式后，**`[NEXT]` 自身变成可机检的投影**——检查器能核对它陈述的事实是否成立。疑问句做不到。

### 形态建议（丢问号，但保留「决策点可见」）

```
现在（错）：ask: 审计已闭环（待修=0），封板？(y/N，无倒计时)

改成（对）：fact: 审计已闭环（待修=0）；封板与否由你决定
           options:
             - k3dge milestone seal M10   （封板：align→归档+版本→指针）
             - 不做                        （里程碑继续挂着）
```

关键：**陈述的是「决策权归属」，不是发问**。
`audit_needed` 已是此形状且工作良好，可作模板：
`"未审计不可封板（封=归档+版本+指针，非界限）：先 k3dge milestone audit <id>"`

### 现状：两条路线杂糅（非有意设计）

```
疑问式 5 个：pending_findings, audit_suggested, seal_ready, audit_open, new_domain
陈述式 7 个：normal, ratchet_open, doc_audit, audit_needed, escalated, sealed, seal_declined
```

### 四条可机检不变量

```
1. [NEXT] 的 fact/note 不得以 ？ 结尾
2. [NEXT] 不得出现 "y/N"、"倒计时"（prompt 词汇，误植即错）
3. 有 options 的态必须 ≥2 个选项（否则＝只给一条路＝下令）
4. 仅播报态（无 options）不得有分支
```

⇒ 这四条合起来，就是 S6「投影给判断主体的形态约束」的**可执行版本**。

> **后续（2026-09-17）**：用户裁定 **B：只删装饰词**——上表不变量 2 已落地（3 处 `ask`
> 的 `(y/N，无倒计时)` / `(倒计时默认修)` 已删），并加了一条守卫测试
> （`test_next_channel_vocabulary` 类：显示串不得含 `y/N` / `倒计时`）。
> 不变量 1、3、4（问号、选项数、播报态无分支）**仍未做**（无实测危害）。

### 两条对偶的形态约束（S6 + S7 合并）

| 投影给 | 形态 | 禁止 |
|---|---|---|
| **判断主体** | **成对选项**（开放式）+ 陈述式事实 | 只给唯一动作（那是下令）；问号（无通道时是语法错误） |
| **进程** | **闭集判定**（bool / enum） | 散文（无法机械分支） |

## S8 【已确认影响下游】引用不可移植：词汇硬编码 + 仓相关

### 问题：可配的分割线划错了位置

```
可配（toml）：  声明【哪些步骤】 —— gates.toml / pipeline.toml 的 id 列表
不可配（Py）：  词汇【怎么说】   —— STATE_OPTIONS 文案/pointers、prompt 文本
⇒ 不可配的那一半恰好含「仓相关」内容
```

### 三层污染（证据）

```
① nextstep.py 硬编码 9/12 态指向 k3dge 自家 ADR
     pending_findings → ADR-0025          ratchet_open → ADR-0025 §2.7
     doc_audit        → ADR-0022          audit_suggested → ADR-0004 §2.1.5
     seal_ready       → ADR-0004 §2.1.4   audit_needed → ADR-0004 §2.1.6
     sealed           → ADR-0004 §2.1.4   new_domain   → ADR-0005 §2.8
     audit_open       → ADR-0022

② 模板 AGENTS.md 带 8 个 k3dge ADR 号（0001/0005/0006/0008/0010/0012/0022/0025）
     ⇒ 每建一个新仓，全部继承过去

③ 无闸可查
     pre-commit 只查 docs/** ⇒ AGENTS.md（根目录）不在检查面
```

矛盾之处：模板自己的 `adr-readme.md.template` 写着「k3dge's own ADRs stay in the
k3dge checkout; **do not copy them here**」——而同一个模板的 AGENTS.md 就在违反它。

### 性质：不是「悬空」，是「指错靶」——更糟

```
本仓 ADR 号：0001 0004 0005 0006 0008 0009 0010 0012 0017 0018 0022 0023 0025
下游从 0001 起编号 ⇒ 0001/0004/0005/0006/0022/0025 全部会撞
```

下游的 `ADR-0006` 是**它自己的决策**。agent 按指针去找，**找到的是一个错的决策**。

注：`pure_refs.check_dangling_adr` 能查「悬空」，但查不出「指错靶」——因为文件**存在**。

### 意见：不该让下游配词汇，该让引用便携

```
让下游配 [NEXT] 文案 ⇒ 每仓一套词汇 ⇒ agent 面向的协议碎片化
⇒ 违背 k3dge 作为「协议单一源」的定位（AGENTS.md §12 触发表必须与之对齐）
```

| 写法 | 例 | 下游对吗 |
|---|---|---|
| ✅ 相对引用 | `AGENTS.md §12` | 对（不带外部编号） |
| ✅ 自识别 | `k3dge ADR-0004 §2.1.5` | 对（明确是 k3dge 的） |
| ❌ 绝对裸引 | `ADR-0004 §2.1.5` | **错靶** |
| ❌ 裸引包在命令里 | `k3dge doc where ADR-0025` | **错靶**（在当仓解析） |

便携解析机制本仓已有：`K3DGE_SOURCE` / `.venv/k3dge-source.txt`（下游仓记录 k3dge
检出路径；`gate.sh` 已用它们做一致性校验）⇒ `k3dge doc where --source ADR-0004` 类可直接落地。

### 三条可机检不变量

```
1. pointers / AGENTS.md 不得含【裸 ADR 号】
   ⇒ 须带 `k3dge` 限定，或经 `--source` 解析
2. 检查面须扩到 AGENTS.md（现只查 docs/**）
3. 便携性测试：scaffold 一个临时仓 → 跑 k3dge 命令 → 断言 [NEXT] 的 pointers
   在该仓里「要么可解析，要么自限定」—— 一次抓住 ①② 两层
```

第 3 条最有价值：**把「下游才会暴露的问题」变成能在本仓跑的测试**。

### 补完了投影契约的第三维

| 维度 | 由什么决定 | 约束 |
|---|---|---|
| **目标**（S6） | 谁消费 | 判断主体 → 选项；进程 → 闭集判定 |
| **语法**（S7） | 有无应答通道 | 有 → 疑问句；无 → 陈述句 |
| **范围**（S8） | 在哪个仓消费 | 引用必须便携，不得依赖本仓独有的事 |

⇒ **投影三维契约：说什么（内容便携）、怎么说（语法随通道）、跟谁说（形态随消费者）。**

## S9 方针筛选：不扩无用基建、只追加增强

**方针**（仓内既有形态：规则 02「cost > value, **with evidence**」+ LEFTOVERS「阈值未到不抽」）：

## 我的判断（供后续讨论校准）

1. 事实源**不能完全统一**；能做到「每个事实一个拥有者 + N 投影 + 相等性守卫」
2. 「两分支」（自动化 / 判断）应精确为「**一源 N 投影**」——分支是投影不是源
3. 判断点可降解为判据（S5 前半）：**目标是把判断尽量下推为判据**，残余才是席位判断
4. 抽象时机已到（4 实例），但容器必须**建模 role + purity**，不能用字典拉平（E39 是反例）

6. **大编排器越界**（S6）：把「内部机械步可编排」推广到「agent 工作流可编排」是破坏性的——判别标准：**可编排 ⇔ 归属与判断在同一主体内，且该主体就是编排者**
7. **词汇精度**（写 ADR 时必守）：
   - 「席位」＝署名判断者（审计人/透镜来源/验收），**不能收进 agent**（agent＝使用者，人＝维护者）
   - 「投影」＝派生视图、由源重生成、从不手填（ADR-0025 语境），**不能拿来指消费者**
8. **投影三维契约**（S6+S7+S8）：内容便携 × 语法随通道 × 形态随消费者
9. **可配的是流程，不是词汇**（S8）：词汇属协议，不得碎片化；引用必须便携
10. **方针筛掉了自己的 3 个提案**（S9）：① 统一形状 / ② 载体边界 / fixer 注册表——
