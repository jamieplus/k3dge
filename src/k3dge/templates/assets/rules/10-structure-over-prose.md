# Rule 10: Structure Over Prose — 教训编进机制，不编进文字

Read when: 你发现同一条叮嘱要写第二遍，或同一类纠正/失败重复出现。

## 1. 核心律

文本指令要求读者"注意到、记住、遵守"——三重都会失败。机制（类型、lint、闸、canonical helper、脚本）不需要任何人配合。**同一条规则第二次落笔时，它就该换形态了。**

## 2. 机制阶梯（选得住的最强一级）

1. **让非法状态不可表示**（类型/结构层面编译不过）
2. **CI 红**（lint、`k3dge check`、`.schema.json`、门禁脚本）
3. **canonical helper**（正确做法是唯一顺手做法）
4. **运行时检查**（错了当场炸，带原因）
5. **散文**（以上都真做不到才写进 rules/AUTHORING，且配一个失败案例）

就近参考：本仓把 hash 比较做成 check 闸（2 级）而不是"记得 sync"的叮嘱；契约提取做成 `k3dge sync`（3 级）而不是手抄接口表。**弱守卫会被抄成下一个模板**——所以选你能承受的最强一级。

## 3. 反馈回路（每次纠正过一遍）

- **Capture**：人纠正了你 / 测试红 / 审计发现 → 先判 one-off 还是 pattern。
- **Route**：one-off → 当场改；pattern → 按 §2 落机制；systemic → rules/ 或 ADR（持久设计走 ADR 触发）。
- **Close**：当轮应用，或落成具体 task。记录不路由 = 没发生。

## 4. 反模式（审计可指认）

- 道谢不记账（"我记住了"不持久）
- 记账不路由（笔记里躺着"本该有的 lint 规则"）
- 就事论事不泛化（修了一个实例，模式原地不动）
- **用散文修结构的病**：如果病因是结构，指令本身就是症状——只准结构性修复。

## 5. 边界

- 判断类规则（"要追问"、"要排序"）无法机制化：留散文（k3dit 透镜），本规则不冒充能编码一切。
- 谁写闸：形式闸归 k3dge（结构/一致性）；可数质量是 audit 角色模块内的价值窗（ADR-0005 / ADR-0025），不是独立写闸方。本规则只管"该不该下沉"，不管归属仲裁。
- 同族：`02`（简化）、`08`（设计纪律）、`ADR-0012`（证据链——机制三环节里"消费者+到达"的判据直接适用于"这条规则有没有到达执行者"）。
